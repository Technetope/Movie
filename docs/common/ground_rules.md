# グランドルール（toio集団制御プロジェクト）

本ドキュメントは `docs/robot_specs.md`・`docs/timeline.md`・ロコモーション計算各種資料を共同開発で扱う際の最低限の共通ルールをまとめる。ここに書かれていない例外運用を行う場合は、必ずチームで合意を取る。

## 1. スコープとフェーズ整理
- シナリオ全長は 0–150 秒。`docs/timeline.md` のフェーズ区分（0–30, 30–50, 50–120, 120–150 秒）を唯一のタイムライン基準とする。
- 各フェーズごとに挙動テンプレートを決め、計算・JSON生成は「フェーズ × ロボットID」で完全に決まる状態を目指す。
- 0–30 秒と 130–150 秒で用いる「回転→並行移動→長方形→復帰→135°→位置調整→45°」のシーケンスは、停⽌の有無や速度係数だけを差し替える方針とし、新たな順序を勝手に導入しない。

## 2. 座標系と単位
- **フィールド座標（Position ID）**: `docs/robot_specs.md` のマット座標を唯一の座標系とし、全ての計算・シミュレーション・JSON 出力をこの 2D 絶対座標で行う。左上が (34, 35)、右下が (949, 898)。
- **姿勢の角度表記**: フィールド座標に対するヨー角のみを扱い、単位は度。0°＝上向き（Position ID の -Y 方向）、180°＝下向き。ラジアンを使う場合は型で明示する。
- **単位の固定**: 長さ=mm、時間=秒、角度=deg。JSON やコードコメントでも必ず単位を明記し、暗黙変換を禁止する。
- **整合性チェック**: 衝突・境界判定にはフィールド座標での実寸値（toio フットプリント 72 mm×32 mm と安全マージン）を直接参照し、ローカル座標への変換を行わない。

## 3. 物理・運動制約
- **速度上限**: 直進 200 mm/s、回転 900 deg/s（`docs/robot_specs.md`）。加減速プロファイルは速度上限の 80% をデフォルトとし、上限を使う場合は理由をコメントに残す。
- **寸法と占有**: toio のフットプリントは 72 mm × 32 mm。安全マージンとして各ロボットの占有矩形を縦横 +20 mm 拡張し、その矩形が時空間的に重ならないように軌跡を定義する。
- **境界条件**: フィールド境界から 25 mm のバッファを取り、軌跡生成時にクリッピング処理を必ず実装する。Position ID レンジ外に出る動きは無効。

## 4. 初期配置と ID 付与
- 基本初期配置は 5×4 グリッド、全ロボット 180° 向き。列間隔・行間隔は `docs/field_calculation.md` の値（163 mm × 191 mm）から変更しない。
- 0–30 秒および 130–150 秒の象限シーケンスでは、専用フォーメーションとして 5 行 × 4 列（20 台）を用い、ギャップは `gap_x=10.7 mm`、`gap_y=18 mm` をデフォルトとする。
- ロボット ID は左上から右下へ行優先で採番（例: row-major 1..30）。フェーズごとに使用するサブセットの ID リストを必ず明示する。
- ID と初期 Pose の対応表を単一のソース（例: `data/initial_poses.json`）で管理し、複数ファイルに重複させない。
- JSON 生成ロジックは `gap_x`, `gap_y` を引数化し、象限ごとのフォーメーションを再計算できるようにする。

## 5. フェーズ別動作ルール
- **0–30 秒**: 「最速移動→停止→最速移動」パターン。停止時間は 1–3 秒の範囲でフェーズ仕様に従う。全ロボット同時に動かす場合でも、軌跡占有が衝突しないよう時間シフトを入れる。
- **30–50 秒**: 螺旋展開。速度関数 `v(r) = v_base + k·r` を使い、`v(r)` が 200 mm/s を超えない `v_base` と `k` を選定する。中心定義はフィールド中心 (491.5, 466.5)。
- **50–120 秒**: 群ロボット動作。人領域のポリゴン集合を事前に定義し、経路生成では必ず禁止領域を差し引く。センサーフィードバックを前提にしない。
- **120–150 秒**: 整列→遅いロコモーション。停止を入れない連続シーケンスで 20 秒以内に収める。


## 7. 衝突回避と検証
- シミュレーションまたは計算コードは「時刻 t における各ロボットの占有多角形」を出力し、任意ペアの交差が無いことを自動チェックする。
- 旋回中は円弧半径を考慮し、背面が交差しないようローカルフレームでの旋回中心をモデル化する。
- 複数ロボットが同一点を共有する場合は時間差を 0.5 秒以上確保し、その証跡をログ化する。
- **座標の連続性**: 連続するフレームの `position` 差分は、当該区間の時間差と速度上限から導かれる最大移動量以下でなければならない。瞬間的なジャンプ（瞬間移動）が生じた場合は生成ロジックをエラーとして弾く。
- **回転中の位置固定**: 回転フェーズ中（`use_rotation=true` の間）は位置が変わらないことを検証する。

## 8. データ構造・コード規約
- 型安全を最優先とし、位置/姿勢/速度/時間は専用の構造体で扱う（例: `Pose2D { position_mm: Vec2, heading_deg: f64 }`）。`any` や縦横混在のマップを禁止。
- フェーズ・シーケンスを記述する JSON は以下のカラムを最低限保持する: `robot_id`, `phase`, `segment_index`, `command_type`, `duration_sec`, `speed_mm_per_sec`, `turn_deg_per_sec`, `waypoints`.
- 連続区間の開始時刻・終了時刻を必ず書き、下流のレンダリングや再生が同期できるようにする。

## 9. サウンドとモーションの同期
- 80–95 秒のサウンド開始ロボットは `robot_id` で固定し、軌跡スケジュールと矛盾しないようにする。
- `sound` フィールドの定義は `docs/sound_patterns.md` を唯一の参照元とし、モーションファイルと別々にバラバラ管理しない。

## 10. JSON出力フォーマット
- JSON は `time` 昇順に並んだ `frames` を基本とし、単一セット `{ "frames": [...] }` か、複数セットを束ねる `{ "sets": [{ "id": "...", "frames": [...] }, ...] }` のどちらかで配布する。複数セット形式を使う場合も、送信時は対象セットの `frames` をそのまま `{ "frames": [...] }` として送る。
- `Frame` で利用できるフィールドと別名:
  - `time` または `t` (float, sec): フレームが適用される時刻。
  - `use_position` または `up` (bool): 並進指令の適用有無。`true` の場合のみ座標指定が必須。
  - `use_rotation` / `use_heading` / `ur` / `uh` (bool): 回転指令の適用有無。`use_position` と同時に `true` にしても良い。
  - `x`, `y` (float, mm) または `position.{x,y}`: 並進指令の座標。`use_position=true` のとき必須。
  - `rotation` / `angle` / `ang` (float, deg): 向き。`use_rotation=true` のとき必須。
  - `stop_distance` / `sd` (float, mm): 並進停止距離。省略時 20.0。
  - `angle_tolerance` / `at` (float, deg): 回転許容誤差。省略時 5.0。
  - `sound` (string|null): 効果音 ID。未指定または `null` で無音。
- 使える効果音 ID（8 kHz/16 bit/mono）は `aurora`, `birds`, `cicada`, `crystal`, `dolphin`, `frog`, `geyser`, `insect`, `reef` の 9 種。
- サンプル（単一セット）:
  ```json
  {
    "frames": [
      {
        "time": 0.0,
        "use_position": true,
        "use_rotation": false,
        "x": 0.0,
        "y": 0.0,
        "sound": "aurora"
      },
      {
        "time": 2.0,
        "use_position": true,
        "use_rotation": false,
        "x": 100.0,
        "y": 0.0,
        "sound": null
      },
      {
        "time": 4.0,
        "use_position": false,
        "use_rotation": true,
        "rotation": 90.0,
        "sound": "reef"
      }
    ]
  }
  ```
- サンプル（複数セットをまとめる場合）:
  ```json
  {
    "sets": [
      {
        "id": "toioA",
        "frames": [
          { "time": 0.0, "use_position": true, "x": 0.0, "y": 0.0, "sound": "aurora" },
          { "time": 2.0, "use_position": true, "x": 100.0, "y": 0.0 },
          { "time": 4.0, "use_rotation": true, "rotation": 90.0, "sound": "reef" }
        ]
      },
      {
        "id": "toioB",
        "frames": [
          { "time": 0.0, "use_position": true, "x": 10.0, "y": 10.0, "sound": "frog" },
          { "time": 3.0, "use_position": true, "x": 150.0, "y": 30.0 }
        ]
      }
    ]
  }
  ```
- 各セット内の `frames` は単調増加に並べ、重複タイムスタンプを避ける。省略フィールドは生成系でデフォルト補完する（`stop_distance=20.0 mm`, `angle_tolerance=5.0 deg`）。`sound` を 1 フレームで複数鳴らす必要がある場合はフレームを分割する。

## 11. レビューと承認プロセス
- 新しいモーション計算やコードをマージする前に、上記ルールへの準拠チェックリストを埋める。
- 計算根拠（速度・距離・時間）は必ず Markdown か Jupyter で共有し、値だけを JSON に直書きしない。
- ルール違反や未確定事項を見つけた場合は、即座に `docs/ground_rules.md` をアップデートし、チームに通知する。
